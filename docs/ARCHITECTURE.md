# worktree-sweep — architecture

`worktree-sweep` is a Windows tool in C# on .NET 10 with a WPF window for the interactive mode. It scans a root for stale git worktrees and orphan folders, removes picks recoverably, escalates once per run through `sudo` and Sysinternals `handle.exe` to clear file locks, and offers an unattended `remove <PATH> --json` path for agents.

The rule that shapes it: the scan writes nothing, and the window's view models and the review sequence are pure state machines that never touch the terminal, disk or git. Terms used in a project sense (candidate, orphan, locker, holder, released, Review) are in the glossary in [`README.md`](README.md). The rulings and invariants behind the code are in [`design.md`](design.md).

## Layers

Two projects. `WorktreeSweep.Core` never references WPF or the exe; the exe references Core and CommunityToolkit.Mvvm.

The Win32 calls come from the CsWin32 source generator (`src/WorktreeSweep.Core/NativeMethods.txt`, `allowMarshaling:false`); the PEB offsets are hand-declared constants in `Holders/Peb.cs`, and the COM interfaces `IFileOperation` and `IShellItem` are hand-declared with `[GeneratedComInterface]` in `Recycle/ShellInterop.cs`, since CsWin32 with `allowMarshaling:false` emits pointer-based COM structs.

### `WorktreeSweep.Core` (`src/WorktreeSweep.Core/`)

- **`Git/`**: `GitRunner` runs `git` with the repo-local env cleared (`RepoLocalEnvVars`), `GIT_OPTIONAL_LOCKS=0`, `core.fsmonitor=false`, prompts off (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`) and a 60 s `CallTimeout`, after which git's process tree is killed and a `GitTimeoutException` (a `GitException`) thrown. Every call takes a `CancellationToken`: a cancel kills the same process tree once (shared with the timeout kill), waits at most `CancelGrace` and throws an `OperationCanceledException` naming the command; a timed-out git whose kill fails is reported at once.

  `VolumeStalls` is the scan's one stall set: the first `GitTimeoutException` on a volume (the path's root as spelled, with no I/O) marks it, in discovery's `git worktree list`, `Scanner`'s per-repo look-ups and the signal reads alike, and every later git call on that volume is skipped with a notice. References nothing else in Core.
- **`Discovery/`**: `Discoverer` finds repos, worktree records, containers and orphans, listing worktrees through `DiscoverySeams` and reporting each child it classifies. It never follows a link: a junctioned `.claude` is not a container, and a gitdir that is a dangling link reads as stale. References `Git/`.
  - It matches walked folders to registered worktrees across path spellings (a subst drive, an 8.3 name, a `\\?\` prefix). A registered path matches as spelled or with its parent resolved by `PathResolver` and its leaf in long form; a walked path matches as spelled or keyed below the resolved root without being resolved itself, so a failed resolution never adds an orphan.
  - A worktree git registered through a loopback admin share of this machine (`\\localhost\X$\...`, `\\127.0.0.1\X$\...`, or the machine's own name) is first mapped to its drive (`X:\...`) by `LoopbackShare` inside `PathResolver.Resolve`, before and after the final path is read, so it matches under a local root.
  - `RegisteredCandidate.Path` gives the drive spelling for display, removal and the holder search. `WorktreeRecord.Path` keeps git's spelling, which every git argument naming the worktree (`worktree lock`, `worktree unlock`) must use, since git does not match one spelling against the other.
  - A repo whose `git worktree list` fails, and a `.git\worktrees\{id}` whose `gitdir` file is missing, unreadable or empty (git's list silently leaves that worktree out), become a `DiscoveryError` each. `Scanner` copies them to `ScanReport.DiscoveryErrors`, written as `discovery_errors` in the scan JSON and as `discovery error:` lines under the `--list` table.
  - `PathResolver` also gives `Holders/` its `FinalPath` and `LongPath`, and `Report/` its `ResolveParent` (the parent resolved, the leaf kept in long form), so the `--list` table and the released-marker lookup match any spelling of a path and a junction orphan keeps its own name.
- **`Signals/`**: `SignalReader` reads merge state (best of the local and `origin` default branches, one failing default never hiding the other; `merge-tree` into one `ScratchObjects` folder per worktree, skipped for unrelated histories), dirty counts, upstream, last activity, size (never through a link) and `ParallelMap`, all taking the scan's `CancellationToken`. `ScanStep` names the steps of one candidate's read, which `Scan/` reports. A git timeout skips the rest of that worktree's signals (`SignalReads`). References `Discovery/`, `Git/`.
- **`Report/`**: `ScanReport` and its candidates; the `--list` table (`ReportTable`, whose `Rows` also give the window each candidate's cells, the risk of its MERGE, DIRTY and UPSTREAM cells, and its `RowKind`, `ActiveUnix` and `SizeBytes` for sorting and filtering; `DiscoveryErrorLines` is the one `{path}: {message}` line per discovery error that the `--list` table and the window's notice on the List and Empty screens share, under a title from `ViewModels/DiscoveryErrorsText`); the detail pane's labelled `DetailField`s (`DetailText.Fields`, with local dates; a field with no text is left out, and the one that says what removing loses is flagged `IsLoss`); the scan JSON (`ReportJson`, through `ReportDocument`); and `ReleasedMarker`, which reads and writes the marker file. References `Discovery/`, `Signals/`, `Review/`.
- **`Scan/`**: `Scanner` runs the scan: discovery, per-repo lookups and every candidate's signals in parallel. `Scan` takes an `Action<ScanProgress>` and a `CancellationToken`, both required; `ScanProgress` reports discovering children, the discovered counts, repos looked up, each candidate's step (with the file count during the size walk) and candidates read (with the path just read). A cancel throws `OperationCanceledException`. References `Discovery/`, `Git/`, `Report/`, `Signals/`.
- **`Processes/`**: the ToolHelp `ProcessTable` with its parent chain and exclusions; `LockedPaths` matching; and `ProcessStopper`, which re-checks a process's image name, and its start time when the caller passes one, through the handle it opened before terminating it, so a PID reused by another program, or by a later run of the same one, is never stopped.
- **`Holders/`**: `HolderFinder.Find` lists processes whose current folder is inside a folder (PEB reads for 64-bit and WOW64 processes), and `StopAllowlist` decides which may be stopped. The open-handle half fills the internal `HandleScanner` seam. References `Discovery/`, `Processes/`.
  - `OpenHandles` lists each candidate's File handles by the File type index, names them through `HandleNaming`'s abandonable workers (4 workers, 200 ms per lookup, a hung one cancelled), and asks the file system which processes use the folder.
  - `HandleNaming` takes a caller-owned `LookupAccount` and a start timeout (`NamingOptions`): a worker claims each item with a compare-and-swap before its check runs, a driver that gives up withdraws an unclaimed item and replaces that worker, and a claimed item that has not returned is unsettled in the account until it does. A name found for a disk file after a cancel is kept while the driver waits; a failed or skipped result after a cancel counts as timed out.
- **`Unlock/`**: `SudoConfig` reads the `sudo config` mode, `SudoCommand` builds the elevated and the manual command lines, and `LinePrompt` asks the numbered line prompts (an empty line takes the default, three invalid answers take the safe one, end of input means no). References `Holders/`, `Processes/`.
  - `ElevatedSession` is the elevated side: one scan per round through `ILockerScan` over every process except pids 0 and 4, its own and the tool's chain, a Stop / Close its handles / Skip / Done prompt per locker through `IProcessControl`, until the folders are clear or a round does nothing; it returns `UnlockExit` 0, 3 or 4. A process the file system reports using a folder whose handles cannot be read, and a folder that cannot be opened or whose users cannot be listed (`HandleFindings.RootsWithoutUsers`, reported through `LockerFindings.Unreachable`), are printed and make the exit 3, never 0, also when lockers remain at the end of the session.
  - A process whose handle lookup timed out (`LockerFindings.TimedOut`, a `TimedOutProcess(Process, Pid)` each, unless it is a locker or already printed as unreadable) is printed and makes the exit 3 the same way. Before saying clear the session calls `ILockerScan.WaitForUnsettledLookups` (up to 1 s), and any of the tool's own lookups still unsettled are printed and make the exit 3, not 0. `LockerScan` owns one `LookupAccount` for the session, across the scan and the re-check.
  - `LockerScan` is the production `ILockerScan`: `LockerScan.Elevated()` enables SeDebugPrivilege (an `UnlockException`, exit 1, when it cannot) and runs `OpenHandles.Scan` over the pids, with names read in UTF-16. A locked folder that is gone from an existing drive is clear; one named twice is scanned once.
  - Each locker carries the start time read before the handles are listed. Before Stop or Close the session re-reads it and skips a locker whose PID has exited, now names another start time, or whose start time cannot be read at either point. To close handles the session makes one `ILockerScan.CloseStillHeld` call per locker: `LockerScan` opens the process once (with synchronize access), confirms its start time, checks it has not exited (`ProcessQuery.HasExited`, also used by `ProcessStopper`), resolves the folders once, re-names each handle and passes it to the session's close callback only while it still names a locked file, keeping the process open until every close returns. A close or re-check that throws leaves that handle unclosed and the rest are still closed. `CloseStillHeld` returns the number closed, or `null` when it could not confirm the process (including one that has exited or whose exit cannot be checked), which the session reports as a skip: it looks at the locker again and prints the exited line for one that has exited, else the could-not-be-confirmed line.
  - `IHandleExe` and `HandleExe` are `handle.exe`'s only use: closing one handle (`-c`). `ChildProcess` runs it (found only in fully qualified PATH folders) with a time limit, killing the tree when one outlives it, and runs `sudo` from `%SystemRoot%\System32` attached to the console (`RunAttached`): it polls the result file every 250 ms, gives the process 10 s to exit once the file holds a code, then uses the reported code and leaves the process running, never killing it.
  - `UnlockResultFile` makes the per-run `%TEMP%` result path, writes the elevated session's exit code there create-new (`Write`, `WriteTraced`), reads it (`TryRead`) and deletes it.
  - `UnlockOffer` is the unelevated side, the sweep's one offer: it lists the locked paths, prints the manual command and skips when sudo is not inline or the program runs under `dotnet.exe`, asks, runs `worktree-sweep unlock` through `ISudoRunner` with `--result <file>` (and prints a line when the session reported but did not exit), and maps exit 0, 3 or 4 to an `UnlockOutcome` (any other exit, a declined UAC prompt included, skips).
- **`Recycle/`**: `ShellRecycler` moves a folder to the Recycle Bin through `IFileOperation` on its own STA thread. `LockedHresults` counts only a `PerformOperations` sharing or access failure as a lock, `RecycleRetry` retries a lock after 250, 500 and 1000 ms before it throws `Removal/LockedException`, and `BinCapacityReader` with `RecycleDecider` decides whether an item fits the volume's Recycle Bin or needs a permanent delete. References `Removal/`, `Report/`.
- **`Removal/`**: removing picks from already-answered `Decision`s; it asks nothing. References `Discovery/`, `Git/`, `Recycle/`, `Report/`, `Signals/`, `Unlock/`.
  - `RemovalPlanner` decides each pick's `RemoveAction` (a link loses only the link, a prunable registration is pruned, a folder is recycled when it fits the Bin, else it needs a yes to delete permanently), and `BranchOffers` decides whether a branch may be deleted and with `-d` or `-D`.
  - `TwoPassSweep` is the pure two-pass sweep: it attempts every pick through an `ISweeper`, offers the unlock step once for every `LockedException` (an `UnlockOutcome` from `Unlock/`), retries the locked picks once after an unlock, and on a cancelled token stops after the current pick and marks the rest `Cancelled`; a locked pick the retry pass skips on cancellation is reported through `ISweeper.Skipped`.
  - `Remover.RemovePicks` drives it live through `CandidateRemover` (recycle, permanent delete, link removal, git unlock and prune, a folder that became a link since the scan left in place, a git lock put back when the removal fails) and `FollowUps` (prune and branch notes); `SweepSummary` writes the closing lines. It reports `Progress.Started(Index)` and `Progress.Done(Index, Outcome)`, so the Removing screen shows each pick's outcome as it lands, a failed or cancelled-skipped pick included.
  - `PermanentDelete` is a hand-written walk that never enters a link and clears read-only first, a link removed only after re-checking it is still one, Win32 32 or 5 at any step thrown as `LockedException` naming the first locked path, and a child that vanishes mid-walk counted as gone.
- **`Review/`**: `LossText` words what a removal loses, and `ReviewSession` asks the questions in order and returns the decisions and `ReviewTotals`. It plans an orphan as a skip when a discovery error names its repo's worktree list, its own `gitdir` file or its repo's `.git\worktrees` folder, every path compared resolved, since git may still use that worktree.
- **`Agent/`**: `AgentRemover` is the `remove <PATH> --json` flow, reaching outside the process only through `AgentSeams`. `PathResolution` resolves the path to one registered worktree or a refusal, `WouldLose` words what a removal would lose, `CallerHolds` finds the caller's own process chain among the holders, and `RemoveReport`, `RemoveReportJson` and `RemoveExitCode` are its output. A run owns one `LookupAccount`, passed through `AgentSeams.FindHolders` to the caller scan and the retry scan (even one that threw); a locked retry with unsettled lookups adds a line to `notes`. References most of the others.

### `WorktreeSweep` (`src/WorktreeSweep/`, the `worktree-sweep` exe)

- **`Program.cs`** parses `[ROOT] [--list | --json]` (the window opens on the Choose screen when ROOT is not given; `--list` and `--json` scan the current directory), the agent's `remove PATH --json [--force] [--stop-build-servers]` and the hidden `unlock` with System.CommandLine (usage errors exit 2, failures exit 1), and routes trace warnings to stderr (`WORKTREE_SWEEP_LOG=debug` adds debug traces). `SubcommandHelpAction` wraps the root's help so a subcommand's help leaves out the scan's `ROOT` argument.
- **Encoding:** `ConsoleEncodings` writes a console in UTF-16 through `WriteConsoleW` and a redirected stream in UTF-8 without a BOM. `Console.OutputEncoding` is only ever set to UTF-16, which never changes the console code page the user's shell sees.
- **`ViewModels/`** holds the window's view models (CommunityToolkit.Mvvm), which use no WPF type, dispatcher or thread, so tests drive them without a window. `MainViewModel` owns the `Screen` (Choose, Scanning, Empty, Failed, List, Review, Removing, Results) and the one view model of each screen, which calls back into it through constructor delegates.
  - Its one Scan command serves the folder box on Choose and the root bar over List, Empty, Failed and Results, and stops the scan while Scanning (back to Choose, the box kept and `Root` cleared); a bad folder shows its error on Choose and under the root bar; the title follows the screen. `ScanningViewModel` shows a `ScanSnapshot` (`ScanTally` folds the `ScanProgress` reports into `ScanStepRow`s, `StepState`s and `WorkingRow`s). `RecentRow` is a recent folder on Choose, from `RecentFolders` (`recent.json` under `%LOCALAPPDATA%\worktree-sweep`, at most 5, most recent first), which sits beside `Program.cs` and uses no WPF type.
  - `ListViewModel` takes the `ScanReport`. `Rows` stays in table order, since Review keys its answers on those indexes; `Shown` is the view the grid binds to, the rows the `KindFilter`, Nothing lost and the search let through, in the order `RowOrder` gives for the `SortKey` and direction (a column cycles ascending, descending, table order). Ticks live on the rows, so a ticked row the filters hide stays ticked and goes to Review.
  - The window's workers call `ScanCompleted`, `ScanFailed` and `RemovalFailed` on it, and `OnProgress`, `UnlockStarted`, `UnlockDone` and `Finished` on `RemovingViewModel`, always on the UI thread. A screen's commands do nothing once it is left, and a removal that is dropped is disposed.
- **Window:** with neither `--list` nor `--json`, `Program.Main` (`[STAThread]`) hands the root, or none, to `WindowMode.Run`, which builds the code-only `App` and `Window/MainWindow.xaml`, scans a given root at once (no root: Choose, the box holding the current directory) and exits 0 once the window has closed and a scan the close cancelled has returned (`CloseCancelled`); there is no `App.xaml`, so the SDK generates no second `Main`. Each screen is a panel shown by `EnumVisibilityConverter`; `RiskBrushConverter` tints the MERGE, DIRTY and UPSTREAM cells, their text by default and the pill behind them with the parameter `Background`; `EnumMatchConverter` binds the kind filter's radio buttons to the view model.
  - The List's `DataGrid` marks each header click handled in its `Sorting` handler (`MainWindow.xaml.cs`) and forwards it to `ListViewModel.SortByCommand`, then redraws the sort arrow from the view model, since the grid never sorts its rows itself.
  - `Window/WindowWorkers` holds every background job, reached through `WindowSeams` and an `IUiDispatcher` so tests run it synchronously: the scan on a background thread (it begins when `Screen` becomes Scanning; each scan has its own `CancellationTokenSource`, cancelled off the UI thread, and posts from an older scan are dropped; progress is coalesced to one post per 100 ms and the 1 s elapsed tick posts what was held back), the Recycle Bin sizes when Review opens, and the removal on its own STA thread, whose `UnlockOffer` runs the unlock step in the terminal while the window shows the notice.
  - Every callback it posts turns a throw into the Failed screen. `RequestClose` lets the window close while scanning, cancels instead while removing, and refuses during the unlock step.

Rules the docs and code state: the scan writes nothing and every git call clears the repo-local env (`GitRunner`); junctions are links and are never sized, walked or deleted through; one elevation per run, for every locked pick together. The full list is in [`design.md`](design.md), "Invariants".

## Integration Footguns

- **Change a field of `Candidate`, `RegisteredCandidate`, `OrphanCandidate` or a signal type** → also update `ReportDocument`, the `JSON report` section of `README.md` (which agents read) and `design.md`'s Report section; `ReportJsonTests.WriteJsonCarriesTheReleasedMarker`, `NoCommitsBranchShowsInTableAndJson` and `WriteJsonWritesTheWholeDocument` pin the shape.
- **Change the `unlock` subcommand's arguments in `Program.cs`** → also change `SudoCommand`, which builds the elevated command line; `SudoCommandTests.ArgvPassesCallerPidAndBackslashPaths` pins it. The elevated session matches only backslash paths.
- **Change an exit code** → also change `RemoveExitCode.For` and the codes in `agent-path.md` and `README.md`; `RemoveCommandTests.RemoveExitCodeMapsEachStatus` pins the mapping.
  - The unlock side has its own codes (`UnlockExit.AllClear`, `SomeLeft`, `NothingDone`), mapped to an `UnlockOutcome` by `UnlockOffer`; `UnlockExitTests.CodesAreZeroThreeAndFour` pins them.
- **Change the released marker's file or fields** (`ReleasedMarker.FileName`, `Released`) → the scan reads it through `ReleasedMarker.Find` and `AdminDir`, and `ReleasedMarkerTests` covers the read and the write. The file keeps `released_at` in Unix seconds; the JSON reports show it as an ISO string.
- **A test that runs `git`** must build its command through `GitRunner`, which clears the repo-local env (the `Fixture` helpers do); `GitEnvTests` pins that the runner ignores an inherited repo env.
- **`Holders/Peb.cs` reads another process's PEB at fixed offsets**, guarded by `Peb.EnsureSixtyFourBit`; `HolderFinderTests` exercises it against real child processes.
- **Add a way to stop a process** → it must pass `StopAllowlist.Stoppable` and `HolderFinder.StillSame`; nothing else is stopped unelevated (`agent-path.md`, "Open decisions").
- **Add a Win32 call** → add it to `src/WorktreeSweep.Core/NativeMethods.txt` for CsWin32 to generate; declare it by hand only when the metadata lacks it, with a comment saying why.

## Test locations

- `tests/WorktreeSweep.Tests/` (xUnit v3, run with `dotnet test WorktreeSweep.slnx -c Release --no-build`): `Fixture.cs` builds throwaway repos with real `git` (`Repo`, `CommitFile`, `AddWorktree`, `MakeJunction`, `Registered`, `Scan`) in a fresh folder under `%TEMP%`, or under the repo's `.tmp\` with `Fixture.InRepoTmp()`, and `WaitUntil` and `IsReleased` for tests that wait on another thread or a held file; its `Git` forces the test git isolation and calls `GitRunner.Run`, and `IsolateGitConfig` (once per test process) points `GIT_ASK_YESNO` at a script that answers yes after 0.25 s, so git itself retries a lock-file rename that met a file another process held (as a scanner holds fresh files in `%TEMP%`) for every git call a test makes, product `GitRunner` calls included, and `FixtureTests` pins that. `ScanProgressTests` pin the progress reports and a cancelled scan. `GitRunnerTests` (the cancel kill included) and `GitEnvTests` pin the git runner.
- `DiscoveryTests` pins discovery on `Discoverer.Discover`, including link and gitdir edge cases. `MergeStateTests`, `WorktreeStatusTests`, `SizeTests` and `ReflogTests` pin `SignalReader` through `Fixture.Registered`.
- `ReportTableTests` (a byte-exact golden table), `ReportJsonTests` (a golden scan JSON document) and `ReleasedMarkerTests` pin `Report/`, building candidates by hand in `ReportSamples`. `ScanTests` pin `Scanner` through `Fixture.Scan()`, and `CliTests` run the built `worktree-sweep.exe`.
- `HolderFinderTests`, `StopAllowlistTests` and `AncestorsTests` pin `Holders/` against children they start (`ReadyChild`); `OpenHandlesTests` pin the handle listing and checks on this process's own handles, and `HandleNamingTests` pin the worker pool, its claim and withdraw rules and its account with an injected check.
- `LockerScanTests` (in the "process environment" collection, since they capture traces) pin `LockerScan` on this process's own handles and, through its internal `Func` and `HandleRecheck` constructors, its unreachable-folder and close paths; `OpenHandles.Scan` takes a `pidsUsing` seam for the same reason; its `ElevatedScanFindsTheHolderOfAGreekPath` is Explicit, run elevated by the owner: `sudo dotnet test WorktreeSweep.slnx -c Release --no-build -- --filter-method *ElevatedScanFindsTheHolderOfAGreekPath --explicit on`.
- `ProcessTableTests`, `LockedPathsTests` and `ProcessStopperTests` pin `Processes/`, the live ones against `pwsh` children they start (`SleepingChild`) and never a process found by name.
- `RecycleRetryTests`, `RecycleDecisionTests` and `BinCapacityReaderTests` pin `Recycle/` without the Shell or the real registry. `ShellRecyclerTests` drive the real Shell on a thread with a timeout, and its `RecycleMovesFolderToRecycleBin` is Explicit, run only with the owner's go-ahead (`--explicit on`). The Explicit recycle tests root their fixtures in `%TEMP%` and call `Fixture.SkipUnlessBinRecycles` first, since X:, the repo's volume, deletes instead of recycling.
- `PermanentDeleteTests` pin `Removal/PermanentDelete` on fixtures with junctions, read-only entries, a held file and a folder whose listing is denied. `RemovalPlannerTests`, `BranchOffersTests` and `TwoPassSweepTests` pin the rest of `Removal/` with hand-built candidates and a fake `ISweeper`.
- `SudoConfigTests`, `SudoCommandTests`, `LinePromptTests`, `UnlockExitTests` and `ElevatedSessionTests` (fake `ILockerScan`, `IHandleExe` and `IProcessControl`, scripted input) pin `Unlock/` without running `sudo` or `handle.exe`. `UnlockResultFileTests` pin the result file, `ChildProcessTests` the bounded wait on real children, and `UnlockOfferTests` the offer with a fake `ISudoRunner`.
- `AgentRemoverTests`, `AgentResolveTests` and `AgentRulesTests` pin `Agent/` through `AgentSeams`; `RemoveCommandTests` run the built exe, and two of them are Explicit.
- `RecentFoldersTests` pin `RecentFolders` against files under the test's own temp folder, never the real `%LOCALAPPDATA%`.
- `ViewModels/` and `Window/` hold the view model and window-worker tests, which run without showing a window.
- `tests/WorktreeSweep.Tests/ProcessEnvironment.cs` defines the non-parallel `process environment` collection (`[CollectionDefinition(Name, DisableParallelization = true)]`, joined with `[Collection(ProcessEnvironment.Name)]`) and `InheritedEnv`, which sets process environment variables and restores them on dispose. **A test that sets an environment variable joins this collection**, so no other test's git process inherits the variable.
- `tests/WorktreeSweep.Tests/TraceCapture.cs` collects what is traced while it is alive, for tests that assert on a warning. `Trace.Listeners` is process-wide, so a test class that uses it joins the `process environment` collection too; that keeps listener changes apart, but tests running in parallel can still trace into a live capture, so assertions on its text use `Contains`, never an exact match or `DoesNotContain`.
- Never run the removing mode against a real folder from an agent session; use `--list` / `--json` or fixtures (`CLAUDE.md`).
